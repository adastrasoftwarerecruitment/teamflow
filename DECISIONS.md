# TeamFlow — Architecture Decisions

_Auto-generated by the build agent. Each decision records the rationale so the next engineer understands the choices._

## D-001: Dual-mode database (Turso cloud + local SQLite fallback)

**Decision:** `database/db.js` detects whether `TURSO_URL` is set. If yes, uses `@libsql/client` for cloud SQLite (Turso). If no, falls back to `better-sqlite3` with a local file at `data/planner.db`.

**Rationale:** Local SQLite lets the app run with zero config for development. Turso provides a free cloud-hosted libSQL database with a compatible SQL dialect for production on Render, where ephemeral filesystems would lose local SQLite data on restart.

**All DB helpers are async** (`DB.all`, `DB.get`, `DB.run`, `DB.batch`) so the same route code works with both drivers.

---

## D-002: Session authentication (Cookie + Bearer Token)

**Decision:** Login returns both a session cookie (for web browsers) and a `token` field in the response body (for Capacitor native). The `requireAuth` middleware accepts either.

**Rationale:** Browsers use cookies automatically; Capacitor native apps cannot reliably share cookies with a remote API, so the Bearer token is stored in `Capacitor.Preferences` (or `localStorage` as fallback) and sent via `Authorization: Bearer <token>`.

**Token storage:** `public/js/api.js` `setToken`/`getToken` abstracts this transparently.

## D-003: Attachment storage as BLOBs (not disk files)

**Decision:** `routes/attachments.js` uses `multer` with `memoryStorage()` and writes `file.buffer` to the `attachments.data` BLOB column (5 MB max per file).

**Rationale:** Render.com's free tier has an ephemeral filesystem — files written to disk are lost on redeploy. Storing BLOBs in the database (which lives in Turso) means attachments survive restarts. The download endpoint is authenticated and streams the BLOB from the DB.

## D-004: Push notifications via Firebase FCM (dry-run if unconfigured)

**Decision:** `services/notify.js` wraps `firebase-admin`. If `FIREBASE_SERVICE_ACCOUNT_JSON` (or `_PATH`) is not set, the service logs a warning and runs in dry-run mode (no actual pushes sent, but no crash). In-app notifications are always written to the `notifications` DB table regardless.

**Rationale:** Allows the app to run fully locally without Firebase credentials while still exercising all notification-triggering codepaths.

---

## D-005: Capacitor Android wrapper (no React Native)

**Decision:** Used `@capacitor/core` + `@capacitor/cli` + `@capacitor/android` to wrap the existing vanilla-JS PWA. No framework rewrite.

**Rationale:** The frontend is already a working SPA. Capacitor wraps it as a native WebView app with access to native APIs (push, preferences, haptics, status bar) without a full framework migration.

**App ID:** `com.teamflow.app` — update in `capacitor.config.json` and Android Studio before publishing.

---

## D-006: iOS-style design system (CSS custom properties)

**Decision:** Replaced the old CSS with a token-based system (`--ios-blue`, `--bg-primary`, etc.) with light/dark mode via `[data-theme]` attribute and `prefers-color-scheme` media query. Bottom tab bar replaces the desktop sidebar on mobile.

**Rationale:** iOS visual language is familiar on Android too (Material You is similar). The CSS-only approach works in a WebView without any JS overhead.

---

## D-007: Hourly cron reminders (due-soon + overdue tasks)

**Decision:** `services/scheduler.js` uses `node-cron` to run every hour. It queries tasks due within 24 hours and overdue tasks, then calls `notify()` for all assignees.

**Rationale:** Free tier of Render doesn't support background workers separately, but the Express web service process can run a cron job. The scheduler respects user notification preferences from the `notification_prefs` table.

## D-009: Subsystem isolation enforcement on the server

**Decision:** Every API route checks `req.user.subsystem_id` against the resource's `subsystem_id`. Super admins bypass this check. Regular members and subsystem admins are silently filtered to their own subsystem.

**The frontend NEVER controls which subsystem data is shown** — the server enforces isolation. The `_subsystem` query param is only a browsing hint for super admins.

---

## D-010: `must_change_password` flow

**Decision:** All users created via Admin UI or `scripts/seed.js` (except the super admin on first seed) have `must_change_password=1`. On login, if this flag is set, the app redirects to the change-password screen before bootstrapping the main UI. The flag is cleared on successful password change.

**Rationale:** Common enterprise security requirement. The server enforces it — the client cannot skip it.
